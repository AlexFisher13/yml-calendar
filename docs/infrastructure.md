# Целевая инфраструктура

## Первая production-среда

Один VPS с 1 ГБ RAM запускает минимальный набор системных сервисов:

```text
Internet
   │
 Caddy ── статический React
   │
   └── /api/* → Go backend ── PostgreSQL
```

- Caddy завершает TLS, раздаёт frontend и проксирует API.
- Go backend запускается через systemd одним бинарным файлом.
- PostgreSQL запускается системным сервисом.
- Docker не устанавливается на production VPS.
- Сборка никогда не выполняется на production.
- Swap 1–2 ГБ используется как аварийная страховка, а не рабочая память.

Экспериментальный запуск на 768 МБ допустим только после измерения RSS всех
процессов и проверки сценариев миграции, backup и restore.

## Ограничения ресурсов

- Пул backend ограничен пятью соединениями с PostgreSQL.
- Для PostgreSQL начальная точка: `shared_buffers=64MB`, `work_mem=1MB`,
  `maintenance_work_mem=32MB`, `max_connections=10`.
- На VPS не размещаются Prometheus, Grafana и сборщики логов.
- Логи передаются в journald с ограничением размера.
- Frontend является статическими файлами и не требует отдельного процесса.

Значения PostgreSQL уточняются после измерений. Они не должны применяться
вслепую к серверу с другим объёмом памяти.

## Окружения

- `local` — Docker Compose с PostgreSQL, миграциями, backend и frontend.
- `staging` — проверка миграций и релизных артефактов.
- `production` — пользовательские данные и ручное подтверждение деплоя.

Staging и production не используют общую базу или секреты.

## CI/CD

Pull request:

1. Форматирование, unit- и integration-тесты Go backend.
2. Проверки и production-сборка frontend.
3. Проверка миграций и локальной Docker-конфигурации.

Merge в `main`:

1. Повторить обязательные проверки.
2. Собрать Go-бинарник и статический frontend вне VPS.
3. Создать release bundle с идентификатором Git commit SHA.
4. Задеплоить staging и выполнить миграции и smoke tests.
5. Дождаться ручного подтверждения Production Environment.
6. Загрузить release bundle на VPS во временный каталог.
7. Применить обратно совместимые миграции отдельной командой.
8. Атомарно переключить symlink релиза и перезапустить backend.
9. Проверить health endpoint и зафиксировать версию.

## Секреты

- Секреты не хранятся в Git.
- CI/CD получает их из GitHub Environments.
- VPS хранит только runtime-секреты с ограниченными правами.
- SSH-ключ деплоя имеет минимально необходимые разрешения.
- Логи не содержат токены, пароли или строки подключения.

## Миграции

- Схема изменяется только упорядоченными SQL-файлами, встроенными в backend.
- Команда `calendar migrate` применяет каждую версию транзакционно один раз.
- Миграции проходят на staging до production.
- Production-миграции обратно совместимы с предыдущим backend.
- Разрушительные изменения выполняются отдельными релизами после переходного
  периода.

## Резервное копирование

- PostgreSQL копируется автоматически не реже раза в сутки.
- Резервные копии хранятся вне VPS и шифруются.
- Восстановление регулярно проверяется на отдельной базе.
- Restore runbook обязателен до первого production-релиза.

## Наблюдаемость и rollback

- `/healthz` проверяет backend и PostgreSQL.
- Внешний сервис контролирует доступность HTTPS.
- Контролируются свободное место, RAM и использование swap.
- Предыдущий release bundle сохраняется для отката backend/frontend.
- Откат приложения не откатывает и не удаляет пользовательские данные.
