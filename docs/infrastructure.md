# Целевая инфраструктура

## Первая production-среда

Один VPS запускает Docker Compose:

```text
Internet
   │
 Caddy
   ├── статический frontend
   └── /api/* → backend
                    │
                PostgreSQL
```

Сервисы:

- Caddy завершает TLS, раздаёт frontend и проксирует API.
- Backend запускается из неизменяемого Docker-образа.
- PostgreSQL хранит данные в отдельном persistent volume.
- Служебные задачи создают зашифрованные резервные копии.

## Окружения

- `local` — разработка на компьютере через Docker Compose.
- `staging` — проверка миграций и релизного образа.
- `production` — пользовательские данные и ручное подтверждение деплоя.

Staging и production не используют общую базу и общие секреты.

## CI/CD

Pull request:

1. Сборка backend.
2. Unit- и integration-тесты backend.
3. Проверки и сборка frontend.
4. Проверка миграций и Docker-конфигурации.

Merge в `main`:

1. Повторить обязательные проверки.
2. Собрать backend и frontend.
3. Создать Docker-образы с тегом Git commit SHA.
4. Опубликовать образы в GitHub Container Registry.
5. Задеплоить staging.
6. Выполнить smoke tests.
7. Дождаться ручного подтверждения production Environment.
8. На VPS выполнить `docker compose pull` и `docker compose up -d`.
9. Проверить health endpoints и зафиксировать версию релиза.

## Секреты

- Секреты не хранятся в Git.
- CI/CD получает секреты из GitHub Environments.
- VPS хранит только необходимые runtime-секреты с ограниченными правами.
- SSH-ключ деплоя имеет минимально необходимые разрешения.
- Логи не должны содержать токены, пароли и строки подключения.

## Миграции

- Схема изменяется только Liquibase.
- Миграции проходят на staging до production.
- Production-миграции должны быть обратно совместимы с предыдущим образом.
- Разрушительные изменения выполняются отдельными релизами после переходного
  периода.

## Резервное копирование

- PostgreSQL копируется автоматически не реже одного раза в сутки.
- Резервные копии хранятся вне VPS.
- Для копий определяются срок хранения и шифрование.
- Восстановление регулярно проверяется на отдельной базе.
- Инструкция восстановления документируется до первого production-релиза.

## Наблюдаемость

Минимальный набор:

- healthcheck backend;
- readiness-проверка базы;
- структурированные логи;
- контроль свободного места;
- уведомления о недоступности приложения;
- идентификатор версии приложения в диагностике.

## Rollback

- Предыдущий образ сохраняется с неизменяемым тегом.
- Compose-конфигурация позволяет вернуть предыдущую версию.
- Миграции проектируются так, чтобы предыдущий образ мог временно работать с
  новой схемой.
- Откат приложения не должен автоматически откатывать или удалять данные.
