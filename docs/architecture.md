# Архитектура

## Общий подход

Приложение строится как модульный монолит с независимыми web- и будущим
iPhone-клиентами.

```text
React PWA ─────┐
               ├── REST API / OpenAPI ── Go backend ── PostgreSQL
SwiftUI ───────┘                         │
                                        └── фоновые задачи и уведомления
```

Модульный монолит упрощает транзакции, тестирование и эксплуатацию на старте.
Выделение микросервисов возможно только при появлении измеримой необходимости.

## Компоненты

### Backend

- Go 1.24 или новее.
- Стандартный `net/http` для HTTP API.
- `pgx` для доступа к PostgreSQL без ORM.
- Встроенные упорядоченные SQL-миграции как единственный механизм изменения
  схемы.
- OpenAPI как контракт между клиентами и сервером.
- Интеграционные тесты с PostgreSQL.

Предполагаемые доменные модули:

- identity;
- calendars;
- events;
- reminders;
- holidays;
- import/export.

Модули должны общаться через явные сервисные интерфейсы и не обращаться
напрямую к внутренним таблицам друг друга.

### Frontend

- React и TypeScript.
- Клиент генерируется или типизируется на основе OpenAPI.
- Адаптивный интерфейс и PWA.
- Серверное состояние отделено от локального состояния интерфейса.

### iPhone-клиент

SwiftUI-клиент является будущим отдельным потребителем того же API. Его
появление не должно требовать изменения базовой архитектуры backend.

## Начальная модель данных

- `User` — учётная запись.
- `Calendar` — контейнер событий.
- `CalendarMember` — доступ пользователя к календарю и его роль.
- `Event` — событие со временем или на весь день.
- `EventParticipant` — участник события.
- `Reminder` — правило напоминания.
- `RecurrenceRule` — повторение в формате, близком к RRULE.
- `HolidaySet` — набор праздников и переносов рабочих дней.

## Даты и время

- Моменты времени передаются и сохраняются в UTC.
- IANA time zone события или календаря хранится отдельно.
- События на весь день используют тип даты без времени.
- Повторения рассчитываются с учётом часового пояса.
- API использует ISO 8601.

## API

- REST API версионируется через путь `/api/v1`.
- Ошибки имеют единый машиночитаемый формат.
- Изменяющие запросы валидируются на сервере.
- OpenAPI обновляется вместе с реализацией.
- Клиенты не обращаются напрямую к базе данных.

## Переход от прототипа

Файлы `index.html`, `favicon.svg` и `calendar-data-example.yml` остаются в корне
до переноса функциональности. YAML станет поддерживаемым форматом импорта и
экспорта, а PostgreSQL — основным источником данных.

## Качество

- Бизнес-правила покрываются unit-тестами.
- Работа с базой и безопасность покрываются integration-тестами.
- Критические пользовательские сценарии покрываются end-to-end тестами.
- Любое изменение схемы сопровождается новой встроенной SQL-миграцией.
